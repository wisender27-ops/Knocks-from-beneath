# Knocks from Beneath — Бэклог рефакторинга

> Доска задач для постепенного приведения кода в порядок.
> Формат: как на работе. Берёшь один тикет, делаешь, проверяешь в Unity, отмечаешь `[x]`, идёшь дальше.
> Код пишешь сам. Здесь — что и зачем делать, на что не наступить, и как понять, что готово.

---

## Правила безопасности Unity (читать перед КАЖДЫМ тикетом)

Unity хранит ссылки на скрипты и поля не по тексту, а по идентификаторам. Поэтому:

1. **Каждому `.cs` соответствует `.cs.meta`.** Если удаляешь скрипт — удаляй и его `.meta`. Если переименовываешь файл — `.meta` переименуется сам, когда сделаешь это *внутри* Unity (в Project-окне), а не в проводнике.
2. **Имя `public`/`[SerializeField]` поля — это контракт со сценой.** Переименуешь `public float speed` → `public float moveSpeed` — Unity потеряет значение, выставленное в инспекторе (станет default). В этих тикетах, где такое требуется, об этом сказано явно и есть шаг «перевыставить в инспекторе».
3. **Имя класса = имя файла.** Класс `PlayerController` должен лежать в файле `PlayerController.cs`. Если переименовываешь класс, который висит на объектах сцены, — делай это через Unity (он умеет чинить ссылки), иначе компонент на префабе станет `Missing Script`.
4. **После каждого тикета:** Unity должна скомпилироваться без ошибок (Console пустая от красного), и сценарий, которого касался тикет, должен отыгрываться как раньше. Это и есть приёмка.
5. **Коммить по одному тикету.** Один тикет = один коммит с понятным сообщением. Если что-то сломалось — откатываешь ровно один тикет, а не неделю работы.

## Состояние кода (диагноз)

Это типичный «code-jam» проект: рабочий, но хрупкий. Главные болячки:

- **Два god-класса.** `IntroSequence.cs` (398 строк) дирижирует всей игрой; `PlayerInteraction.cs` (436 строк) — каскад `if` на все типы взаимодействий.
- **Связь «все обо всех».** 8 синглтонов, ~10 `FindObjectOfType`, 153 public-поля как глобальные переменные, почти неиспользуемый `GameEvents`.
- **Дубли.** Настройка `Rigidbody` при подборе скопирована 3 раза; рейкаст продублирован; проверка «правильный ли предмет для квеста» написана в нескольких местах по-разному (часть — через хрупкий `questTitle.Contains("лом")`).
- **Мусор.** Пустые `TestTrigger.cs` / `BedSleepTrigger.cs`, мёртвый `Quest.cs`, закомментированный код, битая кодировка в комментариях, дублирующийся текст в `MonsterTimer.cs`.
- **Магия.** 50+ «магических чисел» (задержки, силы, дистанции) разбросаны по коду без имён.
- Нет `namespace`, нет `.asmdef`, нет тестов.

Идём снизу вверх: сначала безопасная чистка (нулевой риск для сцен), потом дедупликация, потом аккуратная архитектура.

## [ ] T-01 — Удалить мёртвый код и пустышки

**Зачем.** Эти файлы ничего не делают, но создают шум и сбивают с толку («а это где используется?»). Меньше файлов — меньше места, где прятаться багам.

**Что удалить** (вместе с парным `.cs.meta`!):
- `Assets/Scripts/Events_and_Triggers/TestTrigger.cs` — пустой `MonoBehaviour`, тело класса пустое.
- `Assets/Scripts/Events_and_Triggers/BedSleepTrigger.cs` — вообще без класса, только `using`.
- `Assets/Scripts/QuestSystem/Quest.cs` — мёртвый класс `Quest` (поля `title/goalAmount/...`). Реально игра использует `QuestManager.QuestData`, а не его. Проверено: тип `Quest` нигде не упоминается, кроме собственного объявления.

**Перед удалением — самопроверка (важная привычка):**
- В Unity открой Project-окно, найди каждый скрипт, ПКМ → **Find References In Scene**. Должно быть пусто. (Для `Quest.cs` это особенно важно — убедись, что он реально ни на чём не висит. Он не `MonoBehaviour`, так что висеть и не может, но привычку выработай.)
- `TestTrigger`/`BedSleepTrigger` — `MonoBehaviour`. Если вдруг `Find References In Scene` что-то находит (висит на пустом объекте «на будущее») — сними компонент с объекта, потом удаляй скрипт.

**Как удалять правильно.** Удаляй файлы **из Project-окна Unity** (он сам уберёт `.meta`), а не из проводника. Если уже удалил в проводнике — удали осиротевший `.meta` руками.

**Definition of Done.**
- Трёх файлов нет, осиротевших `.meta` нет.
- Console компилируется без ошибок и без новых warning'ов про Missing Script.
- Игра запускается, ничего визуально не изменилось.
- Коммит: `chore: remove dead scripts (TestTrigger, BedSleepTrigger, Quest)`.

**Чему учит.** Как Unity связывает `.cs` и `.meta`; как проверять «используется ли это» через Find References; дисциплина атомарных коммитов.

# СПРИНТ 1 — Дедупликация (риск: низкий, имена полей не трогаем)

## [ ] T-03 — Единый источник истины: «нужен ли этот предмет текущему квесту»

Это первый «настоящий» тикет с кодом. Тут есть и латентный баг, и дубль — почини оба.

**Контекст / в чём проблема.**
Проверка «правильный ли предмет для активного квеста» сейчас живёт в `PlayerInteraction.cs` в ДВУХ методах и противоречит сама себе:
- `CanPickUpItem()` (строки ~231–237) — гейт «можно ли вообще поднять». Проверяет и `questTag == "crowbar-find"`, и фолбэк `questTitle.Contains("лом")`.
- `PickUpToInventory()` (строки ~210–213) — начисление прогресса. Проверяет **только** `questTitle.Contains("лом")`.

А теперь главное: квесты на предметы создаются в `IntroSequence.cs` **без тега**:
```
CreateQuest("Найти фонарик", 1, OnFlashlightPickedUp);   // строка ~364 — questTag = "" !
CreateQuest("Найти лом", 1, OnCrowbarPickedUp);          // строка ~379
CreateQuest("Найти молоток", 1, OnHammerPickedUp);       // строка ~432
```
Значит проверки `questTag == "crowbar-find"` **никогда не срабатывают**, и весь подбор держится на хрупком `Contains("лом")`. Если кто-то поправит текст квеста (например «Найди монтировку») — подбор молча сломается.

**Цель.** Сделать `questTag` единственным источником истины, а строковые `Contains(...)` убрать. Для этого надо (а) проставить теги при создании квестов, (б) свести проверку в одно место.

**Шаги.**

1. **Проставь теги** в `IntroSequence.cs` у трёх квестов на предметы (передаётся последним аргументом — посмотри, как это уже сделано для `"trash-collect"`, `"box-delivery"` и т.д. в том же файле):
   - «Найти фонарик» → `"flashlight-find"`
   - «Найти лом» → `"crowbar-find"`
   - «Найти молоток» → `"hammer-find"`

2. **Заведи enum для типов предметов, если его ещё нет как общего.** Сейчас `ItemType` уже используется (`item.itemType == ItemType.Crowbar`). Хорошо — переиспользуй его, новый не плоди.

3. **Сделай один метод-источник истины.** Хороший дом для него — `QuestManager` (он и так знает про активный квест). Добавь публичный метод примерно такого контракта:
   ```csharp
   // Возвращает true, если активный квест ждёт именно этот тип предмета (по questTag).
   public bool ActiveQuestWantsItem(ItemType type)
   ```
   Внутри: взять активный квест (с проверкой границ `currentQuestIndex < questList.Count`), сматчить `questTag` → `ItemType`:
   `"crowbar-find"`→`Crowbar`, `"hammer-find"`→`Hammer`, `"flashlight-find"`→`Flashlight`.
   Никаких `Contains`. Соответствие тег↔тип держи в одном месте (например `switch` или маленький `Dictionary`).

4. **Перепиши оба места в `PlayerInteraction`** так, чтобы они звали `QuestManager.Instance.ActiveQuestWantsItem(item.itemType)`:
   - `CanPickUpItem()` — стало `return QuestManager.Instance != null && QuestManager.Instance.ActiveQuestWantsItem(item.itemType);`
   - В `PickUpToInventory()` блок «начислить прогресс» — то же условие. Теперь гейт и начисление используют **одну** проверку, и рассинхрон невозможен.

5. **Удали** строковые `questTitle.Contains("лом"/"молоток"/"фонарик")` из `PlayerInteraction`.

**На что не наступить.**
- `questTag`/`questTitle` — это поля `QuestData`, их **имена не меняем** (иначе слетит инспектор у уже расставленных квестов). Мы только начинаем их корректно *заполнять* и *читать*.
- Не трогай другие теги (`trash-collect`, `box-delivery`, `pie-*`, `go-to-bed`) — они уже работают правильно, это образец для подражания.
- Проверь `null` на `QuestManager.Instance` (в коде местами зовут `.Instance` без проверки — не повторяй эту ошибку в новом методе).

**Definition of Done.**
- Подбор фонарика/лома/молотка работает: предмет можно поднять только когда активен соответствующий квест, и прогресс начисляется.
- Поднять предмет «не в свой» квест нельзя (как и раньше).
- В `PlayerInteraction` не осталось `questTitle.Contains(...)`.
- Логика «тег → тип предмета» существует ровно в одном месте.
- Компилируется, сценарий с поиском предметов проходится.
- Коммит: `refactor(quest): single source of truth for item-quest matching via questTag`.

**Чему учит.** Single Source of Truth, устранение латентного рассинхрона, почему сравнение по стабильным id (тег) лучше, чем по человекочитаемому тексту.

## [ ] T-04 — Убрать тройной дубль настройки Rigidbody при отпускании предмета

**Зачем.** В `PlayerInteraction.cs` блок «вернуть физику объекту» (`useGravity=true; isKinematic=false; linearDamping=0.05f; angularDamping=0.05f; constraints=None; ...`) скопирован **трижды**: в `DropObject()` (~291–295), `ThrowObject()` (~340–345) и `ReleaseHeldObject()` (~397–404). Если поменяешь damping — надо не забыть в трёх местах. Классический источник «починил тут, забыл там».

**Что сделать.**
- Вынеси повторяющуюся настройку в один приватный метод, например `void RestorePhysics(Rigidbody rb)` (плюс, если уместно, парный `void ApplyHeldPhysics(Rigidbody rb)` для блока захвата в `GrabPhysicsObject`, где `linearDamping=15f` и т.п.).
- Замени три копии вызовом метода. Сохрани мелкие отличия (где-то `interpolation=None`, где-то нет) — либо параметром, либо оставив эту одну строку на месте вызова.
- Магические `0.05f`/`15f` пока можно оставить как есть (вынесем в T-05) — этот тикет только про дубль.

**На что не наступить.** Поведение должно остаться **идентичным**. Это чистый рефакторинг «извлечь метод», без смены логики. Сверь каждую из трёх копий построчно — нет ли где-то лишней/недостающей строки (это как раз и есть риск таких дублей).

**Definition of Done.**
- Один метод, три вызова.
- Бросок, выкладывание в зону и отпускание ведут себя как раньше.
- Компилируется, играется.
- Коммит: `refactor(interaction): extract Rigidbody restore into one method`.

**Чему учит.** Рефакторинг «Extract Method», DRY, как безопасно объединять *почти* одинаковые куски.

## [ ] T-05 — Вынести магические числа в именованные поля

**Зачем.** По коду разбросаны числа без имени: задержки `WaitForSeconds(0.5f)`, дистанции `2.2f`, damping `0.05f`, пороги таймера `20f/10f` и т.д. Имя объясняет смысл и даёт крутить значение из инспектора без перекомпиляции.

**Что сделать (по одному файлу за подход, не всё сразу).**
- Для значений, которые хочется крутить в инспекторе → `[SerializeField] private float dropBreakDistance = 2.2f;` и т.п.
- Для значений-констант, которые менять не нужно → `private const float HeldLinearDamping = 15f;`.
- Начни с `PlayerInteraction.cs` и `MonsterTimer.cs` — там их больше всего и они нагляднее.

**На что не наступить.** Если делаешь поле `[SerializeField]` — Unity покажет его в инспекторе со значением по умолчанию из кода; это ок. Имена **новых** полей произвольны (на сцене их ещё нет), так что риск нулевой — но не переименовывай уже существующие public-поля заодно.

**Definition of Done.**
- В обработанных файлах нет «голых» чисел в логике (кроме совсем очевидных, типа `0`, `1`, `0.5f` в Lerp).
- Значения совпадают с прежними — поведение не изменилось.
- Коммит на файл: `refactor: extract magic numbers in <File>`.

**Чему учит.** Самодокументирующийся код, `const` vs `[SerializeField]`, отделение «настроек» от «логики».
